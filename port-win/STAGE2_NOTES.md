# Stage 2 — boot the core snapshot from an on-disk .bin (swappable, no relink)

Goal (user): "the snapshot should be a load — I don't want to recompile the C++ to
change it." dartui previously booted ONLY from the snapshot baked into the exe
(`gen_snapshot` → `vm_isolate_snapshot.bin` + `isolate_snapshot.bin` →
`create_snapshot_file.py` → `snapshot_gen.cc` C arrays → linked in). Stage 2 lets it
boot from the two `.bin` on disk instead, so the snapshot can be regenerated and
swapped without recompiling/relinking. Foundation for a future in-app "Recreate
Snapshot" (Stage 3).

## Mechanism

The four snapshot pointers are `extern const uint8_t*` globals in `dart::bin`
(`snapshot_gen.cc`, declared `extern` at `main.cc:43-46`). The VM reads
`vm_snapshot_data` into `init_params` at `Dart_Initialize` and
`core_isolate_snapshot_data` at `Dart_CreateIsolate`. So **reassigning those two
pointers before `Dart_Initialize`** is a clean, self-contained override.

- **`win_host.cpp` (owned): `windart_load_snapshots_from_disk()`** — `GetModuleFileNameW`
  → exe dir; read `vm_isolate_snapshot.bin` + `isolate_snapshot.bin` (raw Win32
  `CreateFileW`/`ReadFile`) into malloc'd **process-lifetime** buffers (the VM does not
  copy them); reassign `dart::bin::vm_snapshot_data` + `core_isolate_snapshot_data`.
  **ALL-OR-NOTHING**: override only if BOTH read fully; else leave both baked (a
  half-swap mixes snapshots from different builds → `Dart_CreateIsolate` rejects).
  JIT snapshots are data-only, so `*_instructions` stay baked (NULL). Logs which path
  (disk vs baked) it took to stderr.
- **`main.cc` (patched, `windart-port.patch`)**: an `extern "C"` decl beside
  `windart_run_ui_host`, and a `DART_UI_HOST`-guarded call `if (!vm_run_app_snapshot)
  windart_load_snapshots_from_disk();` inserted right before `Dart_InitializeParams`
  (after `EventHandler::Start()`). Guarding on `!vm_run_app_snapshot` leaves the
  app-snapshot path (which sets `vm_snapshot_data` itself) untouched.
- **`CMakeLists.txt` (owned)**: a `dartui` `POST_BUILD` `copy_if_different` of the two
  `.bin` from `${GEN}` to `$<TARGET_FILE_DIR:dartui>`, so they land next to the exe.

## Verification (all captured)

1. **Boots from disk** — `dartui workspace.dart selftest` logs
   `snapshot: booting from on-disk .bin (vm=844802 iso=240765 bytes)`; full 9-tab
   selftest passes, exit 0.
2. **Fallback** — both `.bin` moved away → `using baked-in arrays`, selftest passes;
   only one present (half) → `using baked-in arrays` (all-or-nothing); restore → disk.
   Every case exit 0.
3. **Bytes genuinely consumed** — put the isolate snapshot where the VM snapshot is
   expected → the VM deserialized and REJECTED it:
   `clustered_snapshot.cc:5178: Snapshot expects 15694 base objects, but deserializer
   provided 136`. Proves the disk bytes are used; a bad snapshot fails with a clear
   diagnostic (controlled abort), not silent corruption or a wild crash.

## Known behaviour / future refinement

A full-length-but-WRONG snapshot (passes the read, fails at deserialize) **aborts with
a diagnostic** rather than falling back to baked — deliberate: a genuinely bad swapped
snapshot should fail loudly, not silently run stale baked code. A pre-`Dart_Initialize`
snapshot-version/magic check that falls back to baked on mismatch is a possible Stage-3
nicety (when regeneration is driven in-app), not needed now.

## Reproducibility

`tree/` is regenerated by `extract.py` (pristine quarry + `windart-port.patch`). The
`main.cc` hunks were regenerated from a `diff -u` of pristine-vs-tree `main.cc` and
spliced into the patch's `main.cc` section (no hand-authored hunk headers). Confirmed:
`extract.py` re-applies the full patch cleanly (11 files, 0 rejects) and the fresh
`tree/main.cc` contains `windart_load_snapshots_from_disk`.

Owned files changed: `dart_win32/win_host.cpp`, `CMakeLists.txt`, `windart-port.patch`.
(`tree/runtime/bin/main.cc` is gitignored — captured only via the patch.)
